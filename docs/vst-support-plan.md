> **背景**：评估「网页版音乐编辑器能否加载原生 VST 插件」的技术可行性

## 0. 本文档的定位与重启条件

## 1. 结论速览

一句话：**VST 支持 ≠ 加一个功能，而是给项目引入一个原生音频宿主，本质是换赛道。**

| 路径 | 可行性 | 难度 | 是否需放弃纯前端 | 能否保留静态部署 |
| --- | --- | --- | --- | --- |
| 浏览器直接加载 VST | 不可行 | — | — | — |
| A. 本地原生宿主 + 桥接 | 可行但代价最高 | 极高 | 是 | 是（UI 仍可静态托管） |
| B. Electron / Tauri + Native Addon | 可行，工程上最可控 | 高 | 是 | 否 |
| C. 放弃原生 VST，转 Web 插件生态 | 可行 | 中 | 否 | 是 |

---

## 2. 为什么浏览器装不了 VST（根因）

| 障碍 | 说明 |
| --- | --- |
| 加载方式 | VST3 在 Windows 是 DLL、macOS 是 `.vst3` bundle，靠系统动态加载器载入；浏览器沙箱禁止任意路径的原生代码加载与执行 |
| ABI 层面 | VST3 是 C++ 接口（`IPluginFactory` / `IComponent` + COM 式引用计数），浏览器内没有任何桥梁能调用 C++ 虚表 |
| 运行时依赖 | 插件内部常用 SEH / Win32 消息循环、GUI 窗口句柄、文件映射、多线程、AVX/SIMD 指令集，WASM 均无法提供 |
| 音频架构 | 现有音频链路整体跑在 WebAudio（Tone.js）音频线程的 128 帧块上，VST 必须在原生侧自己的音频回调里运行，两套时钟无法直接对接 |

**常见误解排除**：AudioWorklet 只能运行 JS / WASM，无法加载 DLL；WASM 也没有文件系统任意访问、原生窗口与系统调用能力。因此「用 WASM 直接跑 VST」这条路不存在。

## 3. 方案 A：本地原生宿主 + WebSocket 桥接

### 3.1 架构

```
┌──────────── 浏览器（现有 Vue3 UI 可复用）────────────┐
│  UI / 钢琴卷帘 / 混音台 / 工程管理                    │
│  ↓ 控制指令（WebSocket / WebRTC DataChannel）         │
│  ↑ PCM 音频流 / 参数回调                              │
└──────────────────────────────────────────────────────┘
                        ↓ ↑
┌───────── 本地原生宿主进程（C++ / JUCE + VST3 SDK）────┐
│  VST3 Host：插件扫描 / 加载 / 实例化 / 参数 / 总线     │
│  原生音频设备：WASAPI(Windows) / CoreAudio(macOS)      │
│  插件 GUI：原生窗口（在宿主侧独立渲染）                 │
└──────────────────────────────────────────────────────┘
```

### 3.2 模块拆分

1. **插件扫描器**：遍历 VST3 安装目录，解析 bundle / `moduleinfo.json`，产出插件清单。
2. **宿主核心**：实现 `IHostApplication` / `IPlugFrame` / `IComponentHandler`。
3. **原生音频图**：在原生侧建立串联 / 并联 / 侧链信号链，接管目前由 Tone.js 承担的职责。
4. **桥接层**：控制通道（JSON-RPC over WebSocket）+ 音频通道（PCM 流或 WebRTC）。
5. **前端适配**：`src/core/audioEngine.ts` 抽象出「音源后端」接口，支持浏览器 / 原生二选一。

### 3.3 核心难点（按致命程度排序）

| 难点 | 说明 | 缓解思路 |
| --- | --- | --- |
| 实时时钟同步 | WebAudio 音频线程与原生宿主音频回调独立运行，无共享时钟 | 抖动缓冲 + 时间戳对齐 + 动态重采样；延迟必然增加（数十 ms 起） |
| 音频传输 | 浏览器 ↔ 本地进程之间传 PCM | WebSocket 分包 + 环形缓冲；WebRTC 可降延迟但复杂度更高 |
| 插件 GUI | 多数 VST 自绘原生窗口，浏览器无法内嵌 | 宿主侧独立窗口 + 参数回传；或退化为通用参数面板（体验损失大） |
| 崩溃隔离 | 插件崩溃 / 挂起会拖垮宿主 | 插件运行在独立进程（out-of-process hosting），复杂度显著上升 |
| 分发与安装 | 用户需安装本地程序并授权端口 | 需安装器、自动更新、防火墙 / 端口白名单说明 |
| 双平台 | Windows / macOS 需分别编译与测试 | CI 矩阵 + 分平台打包 |

**判断**：方案 A 以极高的复杂度只换来「UI 留在浏览器」，性价比最低，仅当 UI 必须留在浏览器时才考虑。

## 4. 方案 B：桌面壳 + Native Addon（推荐路径）

### 4.1 架构

```
Electron / Tauri 外壳
 ├── 现有 Vue3 前端（几乎零改动复用）
 └── Native Addon（node-addon-api + JUCE）或 Rust 侧 vst3 crate
      └── 原生音频设备 + VST3 宿主
```

### 4.2 关键选型对比

| 选项 | 优点 | 缺点 |
| --- | --- | --- |
| Electron + node-addon-api + JUCE | 前端复用度接近 100%，生态成熟、调试方便 | 包体大（100MB+），音频设备层需自研 |
| Tauri + Rust `vst3` crate | 包体小、内存安全、进程管理好 | Rust 侧 VST3 生态较新，宿主细节需自研，前端需处理 IPC 边界 |

### 4.3 对现有代码的改造点

- [audioEngine.ts](file:///d:/Data/文档/demo/muisc-editor/src/core/audioEngine.ts)、[instruments.ts](file:///d:/Data/文档/demo/muisc-editor/src/core/instruments.ts)、[effects.ts](file:///d:/Data/文档/demo/muisc-editor/src/core/effects.ts)、[audioStore.ts](file:///d:/Data/文档/demo/muisc-editor/src/core/audioStore.ts) 需抽象为**可替换的音频后端**：
  - 后端 1：现有 Tone.js（浏览器内）
  - 后端 2：原生宿主（VST3）
- [recorder.ts](file:///d:/Data/文档/demo/muisc-editor/src/core/recorder.ts) 与 [wav.ts](file:///d:/Data/文档/demo/muisc-editor/src/utils/wav.ts) 的离线渲染路径，在原生后端下改由宿主完成（需保证实时与离线听感一致，与现有双总线设计同思路）。
- [persistence.ts](file:///d:/Data/文档/demo/muisc-editor/src/core/persistence.ts) 的工程数据结构需新增「插件引用 + 插件状态（chunk / 参数）」字段。
- [types/index.ts](file:///d:/Data/文档/demo/muisc-editor/src/types/index.ts) 需处理**插件未安装**场景：降级为占位轨并保留参数快照，避免工程打不开。
- 需要处理旧工程兼容：新增字段一律可选，缺失时补默认值，符合现有兼容规范。

### 4.4 难度评级

整体 **高**。难点集中在原生音频线程、插件崩溃隔离、双平台打包；前端部分反而是最容易的一环。

## 5. 方案 C：Web 插件生态（不放弃纯前端）

- **WAM 2.0**（Web Audio Modules）：浏览器内的插件规范，运行于 AudioWorklet。
- **WASM 移植合成器**：如 Surge XT 的 wasm 端口等。
- **SF2 / SFZ 采样库**：与现有自定义音源采样体系（IndexedDB 存 PCM）可直接衔接扩展。
- 结论：音色数量与专业度不如 VST 生态，但**零架构改动、可继续静态部署**，是「只想要更多音色」场景的最优解。

---

## 6. 即使现在不做，也值得顺手预留的低成本抽象

以下改动属于架构健康度改进，**与 VST 无强绑定**，可在 main 分支择机实施（本分支不实施）：

1. **音源 / 效果器后端抽象接口**：把 `instruments.ts` / `effects.ts` 收敛到统一接口（create / release / setParam）。
2. **工程数据插件占位字段**：`plugins: []` 可选字段 + 数据版本号，向后兼容。
3. **音色标识分层**：区分「内置音色 id」与「外部插件 id」，为多后端并存做准备。
4. **混音总线数据化**：若当前信号链存在硬编码，改为数据驱动，便于迁移到任意后端。

## 7. 分阶段路线（仅在重启后执行）

| 阶段 | 目标 | 产出 | 通过门槛 |
| --- | --- | --- | --- |
| Phase 0 | 验证可行性 | 最小 PoC：加载 1 个 VST3 并出声 | 能扫描、加载、出声、改参数 |
| Phase 1 | 宿主核心 | 插件管理 + 参数持久化 + 崩溃隔离 | 插件崩溃不影响宿主存活 |
| Phase 2 | 集成编辑器 | 桌面壳 + 工程文件插件字段 | 工程可保存 / 重开且插件状态还原 |
| Phase 3 | 音频图 | 串联 / 并联 / 侧链 / 自动化接入原生后端 | 与现有混音、自动化功能对齐 |
| Phase 4 | 双平台分发 | Windows / macOS 构建 + 安装器 + 更新 | 用户可一键安装并使用 |

## 8. 风险与止损条件

**主要风险**

- 实时音频同步导致体验劣化（延迟、爆音），用户不接受。
- 插件兼容性长尾（各厂商合规性差异）导致维护成本失控。
- 由 Web 转向桌面，失去「打开浏览器即用」的核心优势，与项目定位冲突。

**止损条件（触发即放弃该路径）**

- Phase 0 PoC 端到端延迟 > 50ms 且无法压降。
- 插件崩溃隔离无法稳定实现。
- 维护成本超出单人项目可承受范围。
